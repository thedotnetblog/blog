エージェント開発における最も陥りやすい間違いのひとつは、プロンプトが製品そのものだと考えてしまうことである。

そうではない。

Microsoft Agent Framework チームによる新しい**エージェントハーネスとクロー**のチュートリアルが価値を持つのは、エージェントを使い物にするかどうかを実際に決定する部分、すなわちモデルの周囲のランタイムシェルに焦点を当てているからだ。

それには以下が含まれる:

- ツール
- 計画
- セッション状態
- メモリ
- 実行モード
- イテレーションのための使えるコンソールまたはインターフェース

これこそが、エージェントが単なる巧妙なデモから、実際のソフトウェアのように感じられ始めるポイントである。

## ハーネスパターンは実践的である

私が気に入っているのは、このアイデアがいかにアプローチしやすいかという点だ。

チャットクライアントから始める。

次に、それを指示とツールを持つハーネスでラップする。

そして、計画、TODO、セッション、ストリーミングインタラクションをサポートするシェルを通じて実行する。

これは健全なパターンである。なぜなら関心事を明確に分離しているからだ:

- モデルは推論を担当する
- ハーネスはランタイム動作を担当する
- アプリはどのツールと体験が重要かを決定する

## これは .NET 開発者のシステム構築方法に非常によく適合する

ハーネスのアイデアは .NET の考え方にも見事にマッピングされる。

ランタイム動作が明示的で構成可能である場合、私たちは通常より良い結果を出せる。ミドルウェア、パイプライン、オプション、プロバイダー、アダプターはすべてこの世界で自然に感じられる。

だからこそ、Agent Framework が .NET 開発者に受け入れられる可能性は高いと思う。全員をひとつの魔法の抽象化に押し込めるのではなく、配線可能な構造化されたランタイム部品を提供しているからだ。

## 私の見解

この記事の最も有用な部分は、エージェントには優れたモデルと巧妙な指示文字列以上のものが必要であるというリマインダーである。

エージェントには、構造、メモリ、ツールアクセス、計画、そして機能する開発者ループを与えるランタイムシェルが必要である。

それがハーネスが提供するものである。

そして正直なところ、だからこそこのパターンに注目する価値がある。
