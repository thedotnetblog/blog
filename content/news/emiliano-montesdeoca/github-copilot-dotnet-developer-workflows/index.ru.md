Я думаю, что один из самых полезных сдвигов в освоении Copilot — это уход от одержимости функциями.

Именно поэтому этот новый **гид GitHub Copilot для .NET-разработчиков** работает так хорошо.

Главная идея проста: перестаньте спрашивать, какой режим Copilot самый крутой, и начните спрашивать **какая поверхность подходит к задаче**.

## Это правильная ментальная модель

Для большинства реальной .NET-работы вопрос не в том:

- chat или agent?
- Visual Studio или CLI?
- inline или cloud?

Лучший вопрос звучит так:

- пытаюсь ли я понять код?
- планирую ли я refactor?
- обновляю ли я tests?
- чиню ли я сломанный build?
- координирую ли я изменение, затрагивающее много файлов?

Это куда более продуктивный способ работать с Copilot.

Потому что большая часть путаницы вокруг AI-инструментов возникает из-за того, что поверхности воспринимаются как идентичности, а не как инструменты.

Visual Studio, VS Code, CLI и background agents подходят для разных моментов.

И как только вы это принимаете, весь опыт становится гораздо практичнее.

## Почему это особенно важно для .NET-команд

.NET-работа часто охватывает несколько типов задач за один день:

- понять legacy service
- спланировать refactor
- сгенерировать tests
- починить сломанный build
- одновременно трогать code, config, docs и infrastructure

Это означает, что ни одна отдельная поверхность Copilot не будет лучшей для всего.

Поэтому совет из этого гида хорош, потому что он отражает то, как работа действительно происходит.
