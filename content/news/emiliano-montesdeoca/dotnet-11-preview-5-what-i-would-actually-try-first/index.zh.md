.NET 预览文章总是内容满满。

这对平台来说是好事，但也意味着实际问题被埋没了：**你实际上应该先测试什么？**

.NET 11 Preview 5 在 SDK、运行时、库、ASP.NET Core、C#、MAUI 和 EF Core 中带来了很多内容。我不想把这变成一篇巨大的更新日志回顾——我想聚焦于那些我认为现在值得真正开发者关注的部分。

## MCP 服务器模板进入 `dotnet new` 是一个信号

这可能是 SDK 部分中最具战略性的项目。

当一个项目模板直接进入 SDK 时，意味着平台不再将该场景视为小众。**MCP 服务器模板**内置在 `dotnet new` 中降低了尝试该模式的成本，并向生态发出了一个明确的信号。

如果你正在构建智能体工具、内部助手或 AI 集成的开发者工具，这是我会首先测试的事情之一。

## 构建时的漏洞和生命周期终止检查正是我喜欢的那种默认行为

安全和生命周期意识，最好是在平台在**构建期间**就帮助你，而不是事后在一个没人读的单独报告中体现。

新的 SDK 在构建期间检查漏洞和生命周期终止包，正是我喜欢的那种功能——因为它让更好的行为成为默认。

这些功能不花哨，但它们是那种经得起时间考验的改进。

## C# 在正确的地方继续变得更富表达力

Preview 5 的 C# 项目很有趣，尤其是：

- 封闭类层次结构
- 联合类型声明和联合模式匹配
- 继续推进不安全代码的演进

我不会在生产代码中盲目采纳所有这些——预览语言特性总是需要冷静的测试周期。但方向是好的。C# 持续走向更丰富的建模，同时不失其特性。

## ASP.NET Core 和 EF Core 有值得早期测试的实用更新

两个我肯定会进行 spike 测试的领域：

### Blazor 改进

用于 Blazor SSR 的客户端验证和无需交互性的 QuickGrid 改进，都是那种可以简化真实应用的生活质量功能。

### EF Core 默认值和警告

EF Core 将 SQL Server 2022 兼容性设为默认值，并增加了对异步 EF 查询同步运行的警告——这正是那种能在真实代码库中暴露隐藏问题的变化。

这意味着越早测试越好。

## 我首次体验的短清单

如果我有半天时间来探索 Preview 5，我会这样做：

1. 尝试 MCP 服务器模板
2. 运行构建并检查新的漏洞/EOL 检查
3. 测试可能受益于新 C# 建模特性的代码库
4. 如果你使用 Blazor，验证 Blazor SSR 场景
5. 运行 EF Core 密集路径，观察警告变化或 SQL 差异

这就是我认为早期价值所在。

## 我的看法

.NET 11 Preview 5 感觉像是那种平台同时朝两个方向推进的版本：

- 更雄心勃勃的开发者能力
- 为生产导向团队提供更好的默认值

这种组合正是我从预览周期中想要的。

尝试它，但有目的地尝试。
